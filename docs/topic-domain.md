# 주제 선정 2차 — 경력 연계 후보

> **최종 주제는 [topic-final.md](topic-final.md)** (공정 운전 이상 조사 에이전트). 이 문서는 주제 선정 과정 기록이며, 아래 후보 D의 페르소나·페인포인트는 최종안에 사용하지 않는다. 최종안의 페르소나·페인포인트는 개인 경력과 무관하게 새로 정의했다.

1차 후보([topic-selection.md](topic-selection.md))는 Base 도메인(IT 장애 대응) 위주였다.
2차에서는 **재료화학공학 전공, 고분자 연구소, 화장품 R&D 경험**을 살리는 주제를 찾는다.
선정 조건(일정, 평가 기준, 요구사항 50개, 서비스 3구성)은 1차와 같다.

> 개인정보와 이전 직장 정보는 저장소에 올리지 않는다. 경력은 직무 수준으로만 쓰고, 데이터는 전부 직접 만든 가상 데이터를 사용한다.

## 1. 활용할 경험

| 경험 | 프로젝트에 주는 것 |
| --- | --- |
| 고분자(폴리부텐) 기술연구소: 시제품 물성 평가, 컴파운드 개발, 장기내구성 평가 | 고분자 시험 항목·규격 지식 (용융지수, 충격강도, 색도 등) |

| 과망간산칼륨 소비량 시험 조건·시약 상태 점검으로 **이중시료 RPD 약 15% → 약 3%** 개선 | **"시험 이상 원인 조사"를 직접 해 본 경험** → 페르소나와 시나리오의 핵심 |

| 개인 프로젝트 "제조 품질 시험 데이터 판정 및 해석 도우미" (규격·평균·RSD 계산, PASS/REVIEW/FAIL, LangChain 구조화 출력) | **직접 만든 코드와 경험을 출발점으로 재사용 가능** |
| 6시그마 GB, 산업안전기사, 시험기관 교정 업무 | 통계적 품질관리, 안전 관점의 승인 절차 |

## 2. 핵심 발견: Base 구조와 품질 이상 조사는 1:1로 대응된다

Base는 "장애 알림 → 상태 조회 → 런북 확인 → 원인 분석 → 대응 보고"를 한다.
제조 품질관리 실험실의 **시험 이상(OOS, Out-of-Specification) 조사**도 같은 흐름이다.

| Base (IT 장애) | 품질 이상 조사 (이 프로젝트) |
| --- | --- |
| 장애 알림 ("결제 응답 지연") | 시험 이상 ("PB-1 LOT 2410-07 과망간산칼륨 소비량 이중시료 RPD 14%") |
| `get_monitoring_status` Tool | LOT 시험 결과·규격·통계 조회 Tool, 장비 교정 이력 Tool, 시약 상태 Tool |
| 런북 Resource | 시험 SOP, 이상 조사 가이드, 과거 조사 사례 (RAG) |
| `incident_analysis_prompt` | OOS 조사 표준 절차 (1단계 실험실 오류 확인 → 2단계 공정 조사) |
| 여러 시스템 비교 분석 | 여러 LOT·시험 항목 추세 비교 |
| 재시작·롤백 (위험 조치) | **재시험, LOT 불합격 판정, 리배칭 (QA 승인 필요)** |
| 대응 보고 | **이상 조사 보고서 초안** (원인 후보, 영향 평가, 시정·예방조치) |

→ Base의 그래프·MCP·스트리밍·세션 구조를 그대로 옮기고, **도메인 데이터·MCP 서버·프롬프트만 교체**하면 된다. 1차 후보 A의 장점(일정 내 구현, Base 재사용)을 유지하면서 경력을 살릴 수 있다.

**추천: 후보 D.**

- Base 구조가 그대로 대응돼 1.5일 개발이 가능하고, "Base 로직 + 새 도메인"을 Before로 두면 Before/After를 바로 측정할 수 있다

과제 유형: PDF가 허용한 "Base AI Agent의 주제를 다른 주제로 바꿔 신규 AI Agent로 개발"에 해당한다. Spread에는 신규 프로젝트(2번)로 등록하고, Base 구조를 재사용했다고 명시한다.

## 3-1. 이전 LangChain 실습과 겹치는가?

이전 LangChain 실습 "제조 품질 시험 데이터 판정 및 해석 도우미"와 후보 D는 **도메인은 같지만 푸는 문제가 다르다.**

| | 이전 실습 (판정 도우미) | 후보 D (이상 조사 에이전트) |
| --- | --- | --- |
| 답하는 질문 | "이 측정값은 PASS / REVIEW / FAIL인가?" | "**왜** REVIEW·FAIL이 났고, 무엇을 확인하고 누가 승인해야 하나?" |
| 입력 | 측정값 1세트 | 이상 상황 서술 + LOT 이력, 장비 교정, 시약, SOP, 과거 사례 |
| 구조 | LCEL 체인 1개 + 도구 2개짜리 에이전트 | LangGraph Supervisor + 조사 서브에이전트 병렬 |
| 도구 | 같은 파일 안 `@tool` 함수 | **MCP 서버** 3개 + 외부 MCP 서버 |
| 지식 | 코드 안 규격 dict | SOP·조사 사례 **RAG** |
| 상태 | `InMemorySaver` (재시작 시 소실) | SQLite 체크포인터 + **승인 대기(HITL)** 복원 |
| 품질 보장 | 프롬프트 지시 ("수치를 바꾸지 마라") | 가드 게이트(코드가 수치 교정) + **LLM-as-Judge** + 근거 일치 검사 |
| 서비스 형태 | 노트북 + Gradio | **FastAPI REST + SSE + Vue + LangSmith 대시보드** |
| 저장 | CSV | DB |

### 이전 실습에서 무엇이 디벨롭되는가

1. **"확인하세요"에서 "확인했습니다"로**: 이전 실습은 REVIEW에 "측정 장비의 교정 상태 확인" 같은 **할 일 목록**을 출력했다. 후보 D는 그 항목을 에이전트가 **직접 조회**한다(교정 대장, 시약 대장, 같은 LOT의 다른 시험, SOP). 결과는 근거가 달린 원인 후보로 바뀐다
2. **노트북의 "한계와 개선 방향"을 그대로 해결한다**: 규격 DB화, LOT 단위 추이 분석, 시험방법 문서 검색(RAG), CSV → DB. 이전 실습이 스스로 적어 둔 다음 단계라서, 발표에서 "실습 → 미니프로젝트" 성장 흐름으로 보여줄 수 있다
3. **판정 로직은 재사용 부품이 된다**: 직접 작성한 평균·RSD·판정 함수를 `lims` MCP 서버의 Tool로 옮긴다. 전체 구현에서 차지하는 비중은 작고, 출처를 README에 명시한다

### 주의할 점

- 평가자가 "같은 주제"로 볼 수 있다 → 발표 첫 부분에 위 비교표를 넣어 **새로 만든 부분**을 먼저 보여준다
- 판정 화면을 다시 만드는 데 시간을 쓰지 않는다. 새 기능(조사, RAG, 멀티에이전트, HITL, 스트리밍)에 집중한다

### 완전히 다른 주제를 원한다면

후보 E(화장품 제형 안정성 트러블슈팅)는 "시험값 판정"이 아니라 "제형 문제 해결"이라 겹침이 적다. 대신 화장품 경력 기간이 짧아 데이터·시나리오 작성 부담이 크고, 원료·규제 정보 정확성에 신경 써야 한다.

## 4. 페르소나 (후보 D)

### 주 페르소나 — 입사 1년 차 QC 시험 연구원

| 항목 | 내용 |
| --- | --- |
| 상황 | 출하 전 LOT 시험에서 과망간산칼륨 소비량 이중시료 편차(RPD)가 14%로 기준(5%)을 넘음. 출하 일정은 내일 |
| 목표 | 실험실 오류(시약, 장비, 시험 조건)인지 제품 문제인지 빠르게 가르고, 재시험 여부를 근거와 함께 보고하기 |
| 현재 방식 | 시험 기록 엑셀 → 장비 교정 대장 → 시약 관리 대장 → SOP 문서를 하나씩 열어 확인, 선임에게 질문 |
| 쓰는 화면 | 사용자 프론트엔드 (채팅 + 조사 진행 상황 + 승인 요청) |

### 보조 페르소나 — QA 팀장

| 항목 | 내용 |
| --- | --- |
| 목표 | 이상 조사가 표준 절차대로 근거를 갖춰 이뤄지게 하고, 재시험·불합격 판정은 직접 승인하기 |
| 걱정 | AI가 규격·수치를 지어내거나, 근거 없이 "재시험하면 된다"고 결론 내는 것 (데이터 무결성) |
| 쓰는 화면 | 관리자 대시보드 (LangSmith: 조사 트레이스, 평가 점수, 피드백, 비용) + 승인 요청 |

## 5. 페인포인트 → 해결 기능

| # | 페인포인트 | 해결 기능 | 측정 지표 (Before → After) | 요구사항 |
| --- | --- | --- | --- | --- |
| P1 | **흩어진 기록을 하나씩 열어봐야 한다** (시험 결과, 교정 대장, 시약 대장) | 시험 데이터 / 장비 / 시약 MCP 서버 + 서브에이전트 **병렬 조회** | 조사 소요 시간 | R04~R08, R13, R30 |
| P2 | **증상에 맞는 SOP·과거 사례를 찾기 어렵다** | SOP·조사 사례 **RAG** (키워드 규칙 → 의미 검색) | 원인 후보 매칭 정확도 | R19, PDF 1 |
| P3 | **AI가 수치를 틀리게 말할까 불안하다** | 통계(평균, RSD, RPD, Cpk)와 규격 판정은 **코드가 계산**, LLM은 해석만 → 가드 게이트 | 보고서 수치 오류 수 | R18, R21 |
| P4 | **조사 보고서의 근거가 부족하다** | **LLM-as-Judge** 4기준 + 근거 일치 검사, 필수 항목(원인, 영향, 시정·예방조치) 확인, 미달 시 안내 | 근거 일치율, 평가 점수 | R20~R23 |
| P5 | **재시험·불합격은 승인 없이 하면 안 된다** | **Human-in-the-loop** 승인 (`interrupt`) + 체크포인터로 승인 대기 상태 저장 | 승인 없이 확정된 조치 수 | R33, PDF 4 |
| P6 | **질문 유형이 다양하다** (단순 규격 문의 vs 이상 조사) | **라우팅**: 단순 조회는 바로 답, 이상 조사만 전체 파이프라인 | 라우팅 정확도, 단순 질문 응답 시간 | R16, R17 |
| P7 | **일부 기록이 없거나 조회가 실패하면 멈춘다** | task 단위 **에러 격리**, 확인 못 한 항목을 보고서에 명시, 재시도·폴백 | 장애 주입 시 응답 성공률 | R24~R27 |
| P8 | (QA 팀장) **조사 품질과 비용을 볼 수 없다** | LangSmith Dataset 평가, Feedback, 비용 집계, 프롬프트 Hub | 실험 점수, 요청당 비용 | R39~R44 |

## 6. 진행계획 초안 (Google Spread 등록용, 후보 D)

양식: `순번 | 영역 | 무엇을 바꾸나 | 추가 설명`. 2번 과제이므로 **주제 + 세부 기능 리스트** 형식. 우선순위 **M**(필수) / **S**(권장) / **C**(시간 남으면).

**주제**: 품질 시험 이상(OOS) 조사 에이전트 — Base 장애 대응 에이전트 구조를 제조 QC 실험실 도메인으로 전환하고 개선

| 지표 | Before | After |
