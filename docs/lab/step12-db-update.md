# Step 12 — 규제 DB 갱신 제안 에이전트

## 목표
규제 목록 DB는 확인일(2026-10-20) 기준으로 고정돼 있다. 공식 원본이 개정되면 **에이전트가 새 버전을 찾아 바뀐 행과 제품 판정 변화를 미리 계산**하고, **담당자가 승인해야** DB에 반영한다.
자동 반영하지 않는 이유: 파싱 오류가 판정을 바로 바꾸지 않게, "공식 원본을 사람이 확인한 데이터만 official" 원칙을 지키기 위해서다 ([설계 8·9절](../routing-architecture.md)).

```
detect   : Cellar SPARQL — 감시 목록의 통합본 최신 버전 vs 지금 DB의 버전(행 근거에 적힌 CELEX)
             └ 새 버전 없음 · 이미 올린 버전 → 끝
compare  : 새 버전 원본을 같은 파서로 읽음 → 행 비교(추가·삭제·내용 변경) → 회사 성분 해당 행
           후보를 얹은 임시 DB로 전체 제품 재판정 → 지금 판정과 비교            └ 행 변화 없음 → 기록하고 끝
explain  : LLM이 사실을 승인 담당자용으로 설명 (사실에 없는 숫자·날짜가 있으면 버리고 코드 요약)
propose  : 갱신 후보 저장 (관리자 페이지 "DB 갱신" 탭)
approval : interrupt() — 담당자 결정을 기다림 (체크포인터에 남아 재시작해도 이어짐)
apply    : 승인 → 갱신 파일을 bulk 대신 쓰게 두고 DB를 임시 파일로 만든 뒤 한 번에 바꿔 끼움 / 반려 → 그대로
```

## 만드는 파일

| 파일 | 역할 |
| --- | --- |
| `scripts/import_official_lists.py` (수정) | 통합본 버전(CELEX)을 인자로 — 새 버전을 지금 목록과 같은 파서로 읽는다 |
| `scripts/build_reg_db.py` (수정) | 갱신 폴더(`REG_UPDATES_DIR/bulk/`)의 파일이 같은 이름의 bulk 파일을 대신, DB는 임시 파일 → `os.replace` |
| `app/regupdate/sources.py` | 감시 목록(EU CLP 부속서 VI · REACH 부속서 XVII), 지금 버전, 최신 버전(SPARQL), 새 버전 행 |
| `app/regupdate/compare.py` | 행 비교, 회사 성분 해당 행, 제품 판정 변화, 승인 담당자용 사실 |
| `app/repositories/update_db.py` | 갱신 후보 표 (승인 대기·반영·반려·반영 실패·행 변화 없음) — 같은 버전은 한 번만 |
| `app/agents/update_graph.py` | 갱신 그래프: detect → compare → explain → propose → approval(`interrupt`) → apply |
| `app/service.py`, `app/api/admin.py` (수정) | 확인 실행·결정 재개(`Command(resume=…)`), 시작 시 승인한 갱신으로 DB 재생성 / `/admin/updates` API (대화 승인용 `/admin/approvals` 제거) |
| `app/weekly.py` (수정) | 매주 정기 브리핑 뒤 새 버전 확인 (후보만 — 반영은 승인 후) |
| `frontend/src/admin/*` (수정) | "승인 이력" 탭 → "DB 갱신" 탭: 지금 확인, 후보(판정 변화·회사 성분·바뀐 행), 승인·반려, 이력 |
| `Dockerfile` (수정) | `REG_UPDATES_DIR=/app/state/regulations_updates` (영구 볼륨) |
| `tests/test_regupdate.py` | 행 비교, 갱신 파일 빌드, 감지 → 승인 → 반영 → 재시작, 반려, 지어낸 숫자 |

## 설계 포인트
- **판단은 코드, 설명만 LLM**: 버전 비교·행 비교·판정 변화는 코드가 하고, LLM은 그 사실을 문장으로만 바꾼다
- **승인 전에 결과를 보여 준다**: 후보를 얹은 임시 DB로 제품을 다시 판정해 "승인하면 무엇이 바뀌나"를 먼저 보인다
- **사람이 정리한 행이 우선**: listings.csv가 같은 물질을 덮고 있으면 행이 바뀌어도 판정은 그대로일 수 있다 → 행 비교가 아니라 판정 비교로 확인
- **적용 예정 판**: 통합본 기준일이 오늘보다 뒤면 "아직 적용 전" — 지금 반영할지는 담당자가 정한다
- **반영은 원자적**: 임시 파일에 만든 DB로 한 번에 바꿔 끼운다. 판정은 쿼리마다 DB 파일을 새로 열어 MCP 서버까지 바로 반영되고, 검증에 실패하면 갱신 파일을 되돌리고 DB는 그대로
- 저장소의 bulk 파일은 고치지 않는다 — 승인한 갱신은 갱신 폴더에만 (Docker는 영구 볼륨), 서버가 시작할 때 그 기준으로 DB를 다시 만든다

관리자 페이지(http://127.0.0.1:5173/admin.html) → **DB 갱신** → **지금 확인** (CLP 원본 약 28MB를 받아 10초 안팎).

## 결과 (실제 Cellar, 2026-10-21)

| 목록 | 지금 DB | 최신 통합본 | 바뀐 행 | 제품 판정 변화 |
| --- | --- | --- | --- | --- |
| EU CLP 부속서 VI | 02008R1272-20260701 | **02008R1272-20270101** (적용 예정 판) | 삭제 1: 이산화티타늄(13463-67-7, 022-006-00-2 — 분말 형태 발암성 2) | P002·P004·P010의 CLP "등재 해당" 사라짐 |
| EU REACH 부속서 XVII | 02006R1907-20260622 | 같음 | — | — |

승인하면 등재 9,351행 → 9,350행, 세 제품의 CLP 판정이 바로 바뀐다. 기준일이 2027-01-01이라 지금 반영할지(적용 전 판정을 미리 바꿀지)는 담당자 판단이 필요한 실제 사례다.

## 한계
- 감시 대상은 원본을 기계로 읽을 수 있는 EU 통합본 2종. SVHC 후보 목록·일본 1종(웹 화면만), 국내 목록(별표·첨부 파일)·TSCA·중국은 아직 수동 갱신
- 원본 형식이 바뀌어 파서가 행을 잘못 읽으면 "바뀐 행"이 크게 늘어난다 — 그래서 자동 반영하지 않고 사람이 본다
